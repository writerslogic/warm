# H-B-5 serving contract and hardware evidence

Intel's [Intrinsics Guide performance data](https://www.intel.com/content/dam/develop/public/us/en/include/intrinsics-guide/perf2.js) reports reciprocal throughput0.5cycles for the512-bit `VPDPBUSD` on **Icelake Xeon**, latency5. The client Icelake record is1cycle. The relevant source extract and whole-source SHA256 are preserved in `intel-vpdpbusd-performance.json`. This supports two instructions/cycle as an instruction-throughput ceiling, not as a sustained application rate. At least ten independent accumulator chains are needed merely to hide the5-cycle dependency latency at that issue rate.

Intel's [AVX-512 technology guide](https://cdrdv2-public.intel.com/633930/IntelAVX-512_InstructionSetForPacketProcessing_TechGuide_633930v3.pdf), sections4.2-4.3, explains workload-dependent power/frequency behavior and improvements in third-generation Xeon. It supplies no guaranteed8370C frequency for this workload. The prior VM's2.8GHz nominal receipt is therefore insufficient. At four physical cores and ideal issue rate,100D dots alone require roughly1.744GHz to finish3600seconds,2.092GHz to finish3000seconds, and2.324GHz for2700seconds. Padding to128D multiplies those requirements by1.28. Epilogue, loads and candidate handling add work. These are conditional lower bounds, not an infeasibility claim or a performance result.

Use unsigned **data** codes and signed query codes so correction is query-local, matching the existing WARM VNNI pattern. If data code is `u_i = z_i +128`, query code is `w_i`, and the integer instruction returns `A = sum(u_i*w_i)`, the desired signed dot is `A -128*sum(w_i)`. For100 dimensions and codes in[-127,127], the raw accumulator magnitude is bounded by3,238,500 and the signed dot by1,612,900. An integer-to-float32 conversion of the corrected100D dot is exact, but subsequent scaling is not. Longer dimensions require a checked accumulation bound and widened chunks. Saturating dot instructions are not interchangeable with an exact unsaturated accumulator. Padding uses zero query codes and data code128, with the same query-sum definition; padding100 to128 wastes28% of dot work and is not assumed by the model.

Let the stored reconstruction be `xhat=sx*zx`. Derive an outward error radius from the original source vector, `ex >= ||x-xhat||`, and similarly for the query. An actual scored candidate set yields an upper bound `Uupper` on kth squared distance. The safe pruning comparison is

`lower(||xhat-qhat||²) > upper((sqrt(Uupper)+ex+eq)²)`.

This removes a square root per point: the query's `sqrt(Uupper)+eq` is constant until its incumbent changes. It does not remove per-point floating scaling, norm terms, radius terms or comparisons. Both sides need enclosures following the implemented instruction order. A suitable proof can use directed rounding, exact fixed-point coefficients, or a derived forward-error bound; it cannot treat one unexplained epsilon or successful examples as proof. In particular, a downward-rounded radius is unsafe, cancellation in norm-minus-dot requires an absolute error envelope, integer correction must precede scale evaluation, and overflow/nonfinite metadata must fail explicitly. If enclosures overlap, refine the original row. Exact ties retain the declared tie rule.

The numerical counter preserves H-B-4's quantization and upward float32 reconstruction-error radii. It checks float64 arithmetic against direct float64 L2, with a conservative numerical margin. That establishes tested numeric consistency only. A later serving implementation must prove its own chosen precision and rounding behavior; the counter's broader margin cannot simply be copied into a native certificate.

Intel's official [intrinsic definitions](https://www.intel.com/content/dam/develop/public/us/en/include/intrinsics-guide/data-latest.xml) expose `_mm512_add_round_ps`, `_mm512_sub_round_ps`, `_mm512_mul_round_ps`, `_mm512_sqrt_round_ps` and integer conversion rounding. The guide's rendering code defines negative-infinity and positive-infinity rounding controls together with `_MM_FROUND_NO_EXC`; snapshots and source hashes are in `intel-directed-rounding.json`. These can implement directed enclosures, but availability alone is not a proof of the complete epilogue.

For positive scales, obtain lower/upper products `p_lo <= sx*sq <= p_hi`. The upper endpoint of `2*p*D` uses `p_hi` when integer dot `D>=0`, and `p_lo` when `D<0`, followed by upward multiplication. Downward-add the reconstructed norm lower endpoints, then downward-subtract this dot upper endpoint. Clamp that result at zero, since squared distance is nonnegative. Separately upward-round the square root of the incumbent upper bound, both radius additions and the final square. Only a strict greater-than comparison of the former lower endpoint against the latter upper endpoint permits pruning. Zero dots bypass potentially overflowing scale products. Any NaN, infinity, underflow mode or otherwise unproved lane takes a sound refinement/fallback path; a false comparison must never mean safe rejection.

Flush-to-zero and denormals-are-zero can invalidate directed enclosures. A serving implementation must establish and restore a suitable thread-local floating environment or use a verified fallback that interprets source float32 bits correctly; merely calling a directed-round intrinsic is insufficient. Candidate distances likewise need an actual upper enclosure, not a rounded midpoint, and final top-k intervals that overlap require a defined higher-precision/tie resolution procedure. K can be packed in four-coordinate groups, so100D does not intrinsically require padding to128D.

Seeding uses generic live row IDs, never query identities or synthetic cluster positions. The sample is rebuilt from live membership for this counter, costing a complete live-ID pass. Per-query scores and the current top10 are transient. Seed rows are marked so block refinement does not insert the same ID twice. Exact oracle results are computed only after all serving decisions have completed, for validation and retrospective count ratios. Neither the oracle threshold nor the oracle result set may influence seeding, pruning, refinement or returned results.

The prior Azure E2a process peak was approximately6.53GiB (`streaming-e2a-1/summary.json`), already near the8GiB track limit. The new nominal5.311GB row/code/metadata tally does not replace that observed peak: old PQ lists, training samples, allocator capacities, mappings, ID maps, query scratch and harness state have not been decomposed. A serving design must retire the old approximate structures and measure the complete cgroup peak through insert/delete/reallocation, without assuming that nominal removed bytes equal an RSS reduction. No memory acceptance is granted by this counter.
